This page covers the security architecture of BolkAuth — what attacks are mitigated by default, what you need to configure, and a production hardening checklist.

---

## 🛡️ Threat Model

BolkAuth is designed around a **stateless JWT + database session** model. Here's what is protected out of the box:

| Threat | Mitigation |
|---|---|
| XSS (Cross-Site Scripting) | `HttpOnly` cookies — tokens are never accessible to JavaScript |
| CSRF (Cross-Site Request Forgery) | `SameSite=Lax` cookie flag prevents cross-origin requests |
| Session fixation | New session ID generated on every sign-in |
| Credential stuffing | Constant-time password comparison prevents timing attacks |
| Rainbow table attacks | Per-user random 16-byte PBKDF2 salt — precomputed tables useless |
| Brute-force (passwords) | PBKDF2 with 100,000 iterations makes offline attacks expensive |
| OAuth CSRF | PKCE + random `state` parameter checked on callback |
| JWT tampering | HMAC-SHA256 signature — any modification invalidates the token |
| Session replay after sign-out | Session records deleted from DB on sign-out |

## 🍪 Cookie Security

BolkAuth sets the following flags on the session cookie:

| Flag | Value | Purpose |
|---|---|---|
| `HttpOnly` | ✅ Always | Prevents JavaScript from reading the cookie |
| `SameSite` | `Lax` | Allows GET requests from external sites but blocks cross-origin POST |
| `Path` | `/` | Cookie sent on all routes |
| `Secure` | Automatically set in production | Cookie only sent over HTTPS |
| `Max-Age` | `session.maxAge` (default: 30 days) | Controls when browser expires the cookie |

### When to Use `SameSite=Strict`

`Strict` prevents the cookie from being sent even on top-level navigation (clicking a link from another site). This is the most secure option but will break OAuth flows — the callback from GitHub/Google is a cross-site redirect, and a `Strict` cookie won't be sent.

**BolkAuth uses `Lax` intentionally** to support OAuth callbacks while still preventing CSRF on mutating requests (POST, PUT, DELETE).

## 🔐 CSRF Protection

`SameSite=Lax` prevents most CSRF attacks for modern browsers. However, for API endpoints that accept JSON bodies, BolkAuth additionally validates the `Content-Type: application/json` header — browsers cannot set this header on cross-origin form submissions.

For extra defense-in-depth on custom Server Actions, add explicit origin checking:

```ts
// app/api/sensitive/route.ts
import { NextRequest, NextResponse } from "next/server";

export async function POST(req: NextRequest) {
  const origin = req.headers.get("origin");
  const allowedOrigins = [process.env.NEXT_PUBLIC_APP_URL!];

  if (!origin || !allowedOrigins.includes(origin)) {
    return NextResponse.json({ error: "Forbidden" }, { status: 403 });
  }

  // ... rest of handler
}
```

## 🔑 BOLKAUTH_SECRET Requirements

The `BOLKAUTH_SECRET` is used as the HMAC-SHA256 key for signing JWTs. Requirements:

- **Minimum length**: 32 characters (256 bits)
- **Entropy**: Must be random — do not use a human-readable phrase
- **Storage**: Never commit to source control; use environment variables only

**Generating a cryptographically secure secret:**

```bash
# Using OpenSSL (recommended)
openssl rand -base64 32

# Using Node.js
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"

# Using Python
python3 -c "import secrets; print(secrets.token_urlsafe(32))"
```

### Secret Rotation

If your secret is compromised, rotating it **immediately invalidates all active sessions**. All users will be signed out.

**Rotation procedure:**

```
1. Generate a new BOLKAUTH_SECRET value
2. Update the environment variable in your hosting provider (Vercel, Railway, etc.)
3. Redeploy your application
4. All JWTs signed with the old secret will fail verification — users are logged out
5. Users can sign in again to get new JWTs signed with the new secret
```

> **Zero-downtime rotation** (advanced): BolkAuth supports a `secretsHistory` array in config (coming in v2.0) that allows verification against multiple keys during a rolling rotation window.

## 🔀 OAuth PKCE Flow

BolkAuth implements **OAuth 2.0 with PKCE** (Proof Key for Code Exchange) for all social providers. This prevents authorization code interception attacks.

```
1. User clicks "Sign in with GitHub"

2. BolkAuth generates:
   - code_verifier: 64 random bytes (crypto.getRandomValues)
   - code_challenge: base64url(SHA-256(code_verifier))
   - state: 32 random bytes (CSRF token)

3. User redirected to GitHub:
   /authorize?
     client_id=...
     &redirect_uri=.../callback/github
     &response_type=code
     &scope=user:email
     &state=<random-state>
     &code_challenge=<sha256-of-verifier>
     &code_challenge_method=S256

4. User authorizes → GitHub redirects to:
   /api/auth/callback/github?code=...&state=<same-state>

5. BolkAuth:
   - Verifies state === stored state (CSRF check)
   - Exchanges code + code_verifier for access_token
   - Fetches user profile from GitHub API
   - Creates or links user account in DB
   - Issues BolkAuth JWT session cookie
```

No access tokens are ever stored in the browser — only the final BolkAuth JWT cookie.

## 🏠 Content Security Policy (CSP)

Add a strict CSP header to prevent XSS and data injection. In `next.config.mjs`:

```js
const securityHeaders = [
  {
    key: "Content-Security-Policy",
    value: [
      "default-src 'self'",
      "script-src 'self' 'unsafe-eval' 'unsafe-inline'", // tighten in prod
      "style-src 'self' 'unsafe-inline'",
      "img-src 'self' data: https:",
      "font-src 'self'",
      "connect-src 'self' https://api.github.com https://www.googleapis.com",
      "frame-ancestors 'none'",
    ].join("; "),
  },
  {
    key: "X-Frame-Options",
    value: "DENY",
  },
  {
    key: "X-Content-Type-Options",
    value: "nosniff",
  },
  {
    key: "Referrer-Policy",
    value: "strict-origin-when-cross-origin",
  },
  {
    key: "Permissions-Policy",
    value: "camera=(), microphone=(), geolocation=()",
  },
];

/** @type {import('next').NextConfig} */
const config = {
  async headers() {
    return [
      {
        source: "/(.*)",
        headers: securityHeaders,
      },
    ];
  },
};
```

## 🚦 Rate Limiting

BolkAuth does **not** include built-in rate limiting — this should be handled at the infrastructure or middleware level.

**Recommended options:**

### Vercel Rate Limiting (Edge Config)

```ts
// middleware.ts
import { bolkAuthMiddleware } from "@bolkauth/nextjs";
import { auth } from "@/lib/auth";
import { NextRequest, NextResponse } from "next/server";
import { Ratelimit } from "@upstash/ratelimit";
import { Redis } from "@upstash/redis";

const ratelimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(10, "60 s"),
  prefix: "bolkauth",
});

const authMiddleware = bolkAuthMiddleware(auth, {
  signInUrl: "/sign-in",
  publicRoutes: ["/", "/sign-in", "/sign-up"],
});

export default async function middleware(req: NextRequest) {
  // Rate limit auth API routes
  if (req.nextUrl.pathname.startsWith("/api/auth/sign-in") ||
      req.nextUrl.pathname.startsWith("/api/auth/sign-up")) {
    const ip = req.ip ?? "127.0.0.1";
    const { success, remaining } = await ratelimit.limit(ip);

    if (!success) {
      return NextResponse.json(
        { error: "Too many requests. Please try again later." },
        { status: 429 }
      );
    }
  }

  return authMiddleware(req);
}

export const config = {
  matcher: ["/((?!.*\\..*|_next).*)", "/", "/(api|trpc)(.*)"],
};
```

## ✅ Production Security Checklist

Before going to production, verify each item:

- [ ] `BOLKAUTH_SECRET` is at least 32 characters of random data
- [ ] `BOLKAUTH_SECRET` is stored in your hosting provider's secret management (not in code)
- [ ] `DATABASE_URL` uses SSL (`?sslmode=require` in PostgreSQL connection string)
- [ ] OAuth redirect URIs match your production domain exactly
- [ ] `NEXT_PUBLIC_APP_URL` is set to your production URL (no trailing slash)
- [ ] Rate limiting is enabled on `/api/auth/sign-in` and `/api/auth/sign-up`
- [ ] Security headers (CSP, X-Frame-Options, etc.) are configured
- [ ] `reactStrictMode: true` is set in `next.config.mjs`
- [ ] HTTPS is enforced — `Secure` cookie flag is automatically enabled by BolkAuth when `NODE_ENV=production`
- [ ] Database connection uses a pooler (PgBouncer / Neon Pooler / Supabase Pooler)
- [ ] Error messages returned to the client don't leak internal details (BolkAuth error codes are safe — they don't expose DB details)

## 🔍 Auditing & Logging

BolkAuth emits structured lifecycle events you can hook into for security auditing:

```ts
export const auth = createBolkAuth({
  adapter,
  secret: process.env.BOLKAUTH_SECRET!,
  hooks: {
    onSignIn: async ({ user, session }) => {
      await auditLog.write({
        event: "user.sign_in",
        userId: user.id,
        sessionId: session.id,
        timestamp: new Date(),
      });
    },
    onSignOut: async ({ userId, sessionId }) => {
      await auditLog.write({
        event: "user.sign_out",
        userId,
        sessionId,
        timestamp: new Date(),
      });
    },
    onSignUp: async ({ user }) => {
      await auditLog.write({
        event: "user.sign_up",
        userId: user.id,
        email: user.email,
        timestamp: new Date(),
      });
    },
    onAuthError: async ({ error, path }) => {
      console.error(`[BolkAuth] Auth error on ${path}:`, error.code);
    },
  },
});
```
